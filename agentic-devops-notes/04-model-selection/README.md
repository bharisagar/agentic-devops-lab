# 4. How to choose a model

There is no universally best model for an Agentic DevOps assistant. Choose from evidence produced by a representative evaluation, not a leaderboard alone. Model catalogs, availability, quotas, and prices change; recheck official provider pages before deployment.

## What is a model doing here?

A **generative model** interprets incident context, proposes an allowed next tool, or drafts a report. A **tool-calling model** can return a structured request matching a tool schema, but the application still validates and authorizes it. An **embedding model** converts runbook passages and queries into vectors for semantic retrieval. It may be a different model from the generator.

## Practical comparison checklist

| Criterion | How to test it for this assistant |
|---|---|
| Diagnosis accuracy | Use labeled deployment, container, and Kubernetes incidents with evidence withheld until tools retrieve it. |
| Tool selection/calling | Measure valid schema rate, appropriate tool choice, unnecessary calls, and unsafe requests. |
| Structured output | Require a fixed report schema and count parse/validation failures. |
| Context window | Include realistic logs and retrieved passages; test truncation and distractors. A larger limit does not guarantee better use. |
| Latency | Measure end-to-end and per-call p50/p95 under representative load, including retries. |
| Throughput and quotas | Test expected concurrency and rate limits in the target account/region. |
| Cost | Measure input/output tokens and provider charges per completed investigation, including retries and retrieval/guardrail costs. |
| Privacy and governance | Verify data handling, region, retention, access path, contractual requirements, and approved data classification. |
| Reliability | Test timeouts, malformed output, throttling, provider errors, and fallback/abstention behavior. |
| Retrieval compatibility | Evaluate generator separately from retriever; for embeddings check language/domain suitability and index compatibility. |

Use the same prompts, tool definitions, incident fixtures, retrieved context, and scoring rules when comparing candidates. Keep human review for ambiguous or high-impact cases. Record model/provider identifier, prompt version, and evaluation version so a result can be reproduced.

### Small worked comparison

Imagine candidate A is faster and cheaper, while candidate B handles ambiguous incidents better. Test both on the same 30 labeled, sanitized cases. Include clear failures, missing evidence, irrelevant log noise, and a case where the right answer is to abstain. Record: correct root cause, supported claims, allowed-tool choice, malformed requests, p95 latency, and measured provider charge per completed case. If A is accurate on common cases but weak on ambiguous ones, a simple policy might use A first and route only uncertain cases to B. That policy itself must be tested; a confidence number generated by a model is not automatically calibrated confidence.

### Keep three model jobs distinct

1. **Embedding:** turn each runbook chunk into a vector at indexing time and turn the question into a compatible query vector.
2. **Generation/tool use:** select from allowed diagnostics or write the evidence-backed report.
3. **Optional reranking:** score retrieved candidates for relevance before generation.

These jobs can use different models. A change to the embedding model or vector dimensions generally requires a compatible index and re-embedding plan. A generator upgrade requires regression tests for tool selection, report quality, safety, latency, and cost.

## Hosted, local, and Amazon Bedrock

- **Hosted provider API:** quick to try and usually avoids operating model hardware. Consider network egress, credential handling, provider data policy, quotas, latency, and switching costs.
- **Local/self-hosted model:** can offer more control over deployment and data path, but the team owns hardware, serving, scaling, patching, availability, and performance tuning. “Local” does not itself guarantee privacy or lower cost.
- **Amazon Bedrock:** managed AWS API access to supported foundation models, with IAM integration and AWS-side controls. Model availability and features vary by region/model. Validate exact tool-use, response-format, throughput, guardrail, and data requirements for the chosen model.

Do not select based on “reasoning” branding alone. The selected model must correctly use the specific tools and produce useful evidence-backed reports on your cases. A smaller or cheaper model can be enough for classification or formatting; a stronger model may be justified for harder diagnosis. Routing between models adds complexity and should be evaluated too.

## Safe integration

Keep credentials on the server or use an AWS role; never expose keys in browser JavaScript or source control. Send only necessary context. Apply request timeouts, token limits, schema validation, output checks, and explicit handling for refusal or low confidence. The model does not determine IAM permissions.

For the example, send the model the missing-variable *name* and a short redacted startup excerpt, not all environment variables or an unbounded log archive. Constrain the model’s output to either an allowlisted tool request or a report schema. Reject unknown tool names and malformed JSON, and provide a safe “unable to complete” result if the model/provider times out.

## Interview questions

**How do you compare two candidate models?** Run the same labeled test set and compare task accuracy, valid tool use, unsafe requests, latency, reliability, and cost under the same context and settings.

**Does a larger context window mean a better model?** No. It allows more input, but retrieval quality, attention to relevant evidence, latency, and cost still matter.

**Should the embedding model match the generator?** Not necessarily. Choose an embedding model for retrieval quality and compatibility with the vector index; choose the generator for reasoning, tool use, and response requirements.
